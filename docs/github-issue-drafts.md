# GitHub Issue Drafts

## Node実装のbacklog-apiリポジトリ分離を完了する

### 概要

初期実装では、Backlog MCP Server相当のNode Core/CLIとAgent Skillを、
`backlog-api-skills`リポジトリ内の`src/`と`skills/`に分けて管理していました。

Node実装を`backlog-api`リポジトリへ移し、
`backlog-api-skills`はNode版へAgent向けの判断、安全性、作業コンテキスト、
連携機能を追加するプロダクトとして整理します。ソース移動後に、両リポジトリ
のテスト、runtime固定、文書、リリース境界まで確認して分離を完了します。

### 分離後の責任範囲

#### backlog-api

- Backlog MCP Server相当のNode Core/CLI
- 上流の操作名、入力スキーマ、ハンドラー動作のストレート変換
- JSON入出力、操作カタログ、dry-run、基本的な変更保護
- 上流ソースおよびテストとのトレーサビリティ
- Node単体のビルド、テスト、配布物、リリース
- MITライセンスと上流の第三者通知

#### backlog-api-skills

- `backlog-api`を利用するAgent Skill
- 既定の読み取り専用方針と、追加・更新時の明示許可
- 現在のスペース、プロジェクト、Issueなどの作業コンテキスト
- Issue健全性チェック、メンション、通知の整理支援
- `workplace/`への許可制保存
- `mikuproject`、`miku-md2xlsx`など他のmiku-soft製品との連携
- Node runtimeの取得、固定、Skill bundleへの組み込み

### トレーサビリティ方針

次の二段階で追跡できるようにします。

```text
backlog-mcp-serverのtag／commit／tool
  → backlog-apiのversion／commit／Node operation
  → backlog-api-skillsのversion／workflow／reference
```

`backlog-api-skills`側では、利用する`backlog-api`のバージョン、commit、
成果物名、必要に応じてchecksumを記録します。

### 移行作業

1. `backlog-api`リポジトリをMITライセンスで準備する
2. `src/`、Node用ビルドスクリプト、テスト、上流対応表を移動する
3. Node CLIとruntimeの単独ビルドおよびリリース方法を整備する
4. `backlog-api-skills`が利用するNode版の固定方法を決定する
5. Skill bundleへNode runtimeを取り込む再現可能な処理を追加する
6. 両リポジトリのCIで責任範囲に応じたテストを実行する
7. README、ライセンス、第三者通知、開発資料を分割する
8. 現在の機能と58操作が移行後も維持されることを確認する

### 検討事項

- Node版の初回バージョンと既存`0.3.0`からの扱い
- npmパッケージ、GitHub Release成果物、または別方式によるruntime受け渡し
- Node版更新時にSkill側へ追従する手順
- 上流更新、Node変換、Skill更新それぞれのリリース周期
- 複数リポジトリにおけるライセンスと第三者通知の配置
- 分離中に機能追加をどこまで停止または制限するか

### 完了条件

- `backlog-api`と`backlog-api-skills`の責任分界が文書化されている
- Node Core/CLIが`backlog-api`単独でビルドおよびテストできる
- `backlog-api-skills`が固定したNode runtimeを再現可能に取り込める
- 上流からNode、NodeからSkillへの対応関係を追跡できる
- 58操作、変更保護、配布物、ライセンス情報が移行後も維持される
- 両リポジトリの更新およびリリース手順が文書化されている

- 複数のBacklog組織を利用する場合の設定方法
- ログ、診断情報、エラーにAPIキーが出力されないこと
- `workplace/`や生成物へ認証情報が保存されないこと
- ローカル開発、CI、利用者環境それぞれの設定手順
- APIキーの更新・失効時の運用方法
- ローカル`.env`を採用するか
- `.env`を採用する場合の読み込み方法とファイル権限

- 認証情報が出力・保存されないことをテストする

## Issueの整理と健全性チェックを読み取り専用で支援する

### 概要

期限切れ、長期間停滞している実行中Issue、親Issueの設定漏れなどを検出し、
プロジェクト内のIssue整理を支援する機能を検討します。

既定では読み取り専用で診断し、対象Issue、検出理由、推奨対応を提示します。
追加や更新は自動実行せず、ユーザーが対象と変更内容を確認して明示的に許可
した場合だけ行います。

### チェック候補

- 期限切れ、期限間近、期限未設定
- 長期間更新されていない実行中Issue
- 担当者未設定、または担当者ごとの実行中Issueの偏り
- 親Issueが未設定と思われるIssueと親候補
- 完了済みの親Issueに残っている未完了の子Issue
- 子Issueがすべて完了している未完了の親Issue
- 開始日と期限日の矛盾
- マイルストーン、カテゴリー、バージョン、優先度の設定漏れ
- 説明や完了条件が不足しているIssue
- 類似タイトルを持つ重複Issue候補
- 長期間コメントや活動がないIssue
- 特定ステータスへ長期間滞留しているIssue
- リリース予定のマイルストーンに残っている未完了Issue
- 最近作成、更新、完了されたIssueの日次または週次まとめ

### 安全要件

- 対象スペースとプロジェクトを事前に明示する
- 既定では読み取り専用で実行する
- 推測を含む判定は断定せず、根拠と候補として提示する
- 親Issueや重複Issueの候補を自動確定しない
- 追加・更新前にIssueキー、現在値、変更後の値を表示する
- ユーザーが明示許可した変更だけを実行する
- 取得結果を保存する場合は、保存先と取り扱い上の注意を説明して許可を得る

### 事前調査

- 各チェックに必要なIssue項目をBacklog APIから取得できるか
- 状態変更履歴や最終活動日時を取得できるか
- 親子関係、マイルストーン、カテゴリー、バージョンを更新できるか
- API権限や取得件数、ページング、レート制限上の制約

### 完了条件

- Backlog APIで実現可能なチェック範囲を記録する
- 最初に実装するチェックと判定基準を決定する
- 読み取り専用の診断結果形式を定義する
- 誤検出時に安全に除外または再判定できる

## Backlog Issueとmikuproject WBSの連携を検討する

### 概要

BacklogのIssue情報を`mikuproject`のWBS作成・更新フローで利用できる連携を
検討します。

初期段階では双方向の自動同期を行わず、Backlogから読み取ったIssueを新規
WBS用の`project_draft_view`へ変換するか、既存WBSに対するPatch JSON候補を
作成して、人間が確認できる流れを優先します。

### 利用例

- BacklogプロジェクトのIssueから新しいWBS案を作成する
- 親子IssueをWBSの階層へ反映する
- 開始日、期限日、担当者、状態をWBS計画の参考情報として取り込む
- Backlogの変更から既存WBSに対するPatch JSON候補を作成する
- WBS上の計画変更からBacklog更新候補を提示する
- WBSレビュー、スケジュール調整、レポート出力へ引き渡す

### データ対応の検討事項

- Backlogのスペース、プロジェクト、Issueキーとmikuprojectの`task_uid`の対応
- Issue件名、説明、担当者、開始日、期限日、状態、優先度の対応
- 親子IssueとWBS階層の対応
- Backlogで表現できる関係とWBSの先行タスク依存関係の違い
- 新規WBSでは`project_draft_view`の`predecessor_uids`または
  `predecessors[].task_uid`を使用すること
- 既存WBSの依存関係変更ではPatch JSONの`link_tasks`と`unlink_tasks`を
  使用すること
- 削除、完了、再開、担当変更をどのように差分として扱うか

### 安全要件

- 対象スペースとプロジェクトを明示する
- Backlogからの読み取りを既定とし、自動的に書き戻さない
- 変更候補にはIssueキー、現在値、変更後の値、変更理由を含める
- Backlogへの追加・更新はユーザーの明示許可後だけ実行する
- 競合時に一方を自動的に正として上書きしない
- APIキーをWBS、Patch JSON、対応表へ保存しない
- 取得データや対応表を永続化する場合は保存先を説明して許可を得る
- `mikuproject`のブラウザー上での視覚確認を置き換えるものとしない

### 事前調査

- Backlog APIから取得できるIssue項目、親子関係、履歴の範囲
- `mikuproject`の`project_draft_view`、Patch JSON、workbook状態の対応項目
- Issueキーと`task_uid`の対応表を安全に維持する方法
- 更新時刻や基準スナップショットを用いた競合検出方法
- 一方向インポート、差分提案、限定的な書き戻しの段階的な実装順序

### 完了条件

- 最初に対応する連携方向とユースケースを決定する
- Backlogとmikuprojectの項目対応表を作成する
- Issueキーと`task_uid`のトレーサビリティ方式を決定する
- 競合、欠落項目、変換警告の扱いを定義する
- 許可なしでBacklogが変更されないことをテストする

## 整理したBacklog Issueをmiku-md2xlsxでXLSX出力する

### 概要

Backlogから取得し、確認・整理・要約したIssue情報をMarkdown表へまとめ、
`miku-md2xlsx`を使用して`.xlsx`ファイルとして出力する機能を検討します。

MarkdownからXLSXへの変換は実験的な生成支援として扱い、元のBacklog画面を
忠実に再現するものとはしません。変換処理はローカルで行い、AI APIや外部の
変換サービスを使用しません。

### 利用例

- 期限切れや長期間停滞しているIssueの一覧をXLSX化する
- 自分の担当IssueやメンションされたIssueを整理して出力する
- プロジェクトレビュー用にIssueの状態と推奨対応を表へまとめる
- 日次・週次のIssue整理結果を関係者が確認できる形式にする
- mikuproject連携前の確認資料としてIssue一覧を出力する

### Markdown表の項目候補

- スペース名または識別名
- プロジェクトキー
- Issueキー
- 件名
- 状態
- 担当者
- 優先度
- 親Issueキー
- 開始日と期限日
- 最終更新日時
- 検出理由または整理区分
- 要約
- 推奨対応

利用者が必要な列だけを選択できるようにし、Issue本文、コメント、利用者情報
など注意を要する情報は既定で含めません。

### 出力フロー

1. 対象スペース、プロジェクト、Issueの抽出条件を確認する
2. Backlog APIから読み取り専用で情報を取得する
3. 出力対象、列、件数、伏せる情報をプレビューする
4. 保存先と情報取り扱い上の注意を説明する
5. ユーザーの明示許可を得る
6. XLSX変換用のMarkdown表を生成する
7. `miku-md2xlsx`で単一の`.xlsx`へ変換する
8. 出力件数、保存先、変換時の警告を報告する

### 保存方針

- 既定の出力先は`workplace/`配下の用途別ディレクトリとする
- ディレクトリまたはファイル名へタイムスタンプを付ける
- 既存ファイルを自動的に上書きしない
- APIキーをMarkdown中間データやXLSXへ含めない
- 中間Markdownを保存する場合も別途ユーザーの許可を得る
- 出力ファイルの削除方法と保持上の注意を案内する

### 事前調査

- `miku-md2xlsx`が受け付けるMarkdown表の仕様と制約
- 複数の表やシートを扱う必要があるか
- 長文、改行、リンク、日時、空値の変換方法
- 大量Issueを出力する場合のページングと件数上限
- 個人名、コメント、Issue本文などの既定除外範囲

### 完了条件

- Markdown表の入力契約を定義する
- 出力対象、列、保存先のプレビューを実装する
- 許可なしではMarkdownやXLSXが保存されない
- `workplace/`配下へタイムスタンプ付きXLSXを生成できる
- APIキーや既定除外対象が出力されないことをテストする
- `miku-md2xlsx`の警告と制約を利用者へ報告する
